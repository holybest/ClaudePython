# 테스트 기법별 도출 규칙

`techniques` 필드에는 아래 이름을 그대로 쓴다. 스크립트가 이 이름으로 기법별 통계를 낸다.

| 기법명 | 사용 시점 |
|---|---|
| `동치 분할` | 유효/무효 클래스 대표값 |
| `경계값 분석` | 경계값과 바로 바깥 값 |
| `페어와이즈(PICT)` | PICT 결과 행에서 만든 케이스 |
| `WoW 검증` | 엣지 케이스 |
| `요구사항 분석` | 단순 기능 확인(입력 공간이 없는 동작) |
| `상태 전이` | 상태 기계 요구사항 |
| `고장 주입` | 안전 메커니즘, 진단 |
| `결정 테이블` | 조건 조합으로 출력이 결정되는 로직 |

케이스 하나에 여러 기법을 쓸 수 있다(예: `["경계값 분석", "고장 주입"]`).

## 동치 분할

1. 입력·상태 변수마다 요구사항이 다르게 처리하는 값 집합을 나눈다. 출력이 같아도 처리 경로가 다르면 다른 클래스다.
2. 유효 클래스: 여러 유효 클래스는 한 케이스에 함께 넣어도 된다(케이스 수 절약).
3. 무효 클래스: **한 케이스에 하나씩**. 나머지 입력은 유효한 대표값으로 둔다.
4. 대표값은 경계에서 떨어진 중간값을 쓴다(경계는 경계값 분석이 담당하므로 중복 방지).

예) 요구사항: "차속 0~250 km/h에서 표시, 범위 밖이면 `---` 표시. 신호 해상도 1 km/h"
- 무효(하한 미만): 해당 신호가 음수를 표현할 수 있을 때만. 표현 불가능하면 클래스에서 제외하고 그 사실을 근거로 남긴다.
- 유효: 0~250 → 대표값 120
- 무효(상한 초과): 251~ → 대표값 300 (신호 최댓값 범위 내인지 확인)

## 경계값 분석

- 기본은 2-값 BVA: 각 경계에서 **경계값**과 **바로 바깥 값**(해상도 1단위 차이).
  위 예: `0`, `250`, `251` (그리고 음수가 표현 가능하면 `-1`)
- ASIL C/D 항목이나 경계 근처 동작이 중요한 경우 3-값 BVA(경계 안쪽 값 추가: `1`, `249`)를 쓴다.
- 시간 경계도 경계값이다: "500 ms 이상 지속 시 경고" → 490 ms(tick 해상도만큼 짧게) 미발생, 500 ms 발생.
- 히스테리시스가 있으면 ON 경계와 OFF 경계를 각각 시험한다.
- 해상도·단위·허용오차가 요구사항에 없으면 값을 지어내지 말고 검토 의견에 기록한다.

## 페어와이즈 (PICT)

적용 조건: 독립적인 이산 파라미터 3개 이상, 전수 조합이 시험 예산을 넘을 때. 파라미터가 2개뿐이면 전수 조합이 곧 페어와이즈이므로 PICT가 필요 없다.

모델 파일 예 (`model.txt`, 탭 또는 `:` 구분):

```
IGN:      OFF, ACC, ON
Gear:     P, R, N, D
Speed:    0, 5, 120, 250
Door:     Closed, Open
Seatbelt: Fastened, Unfastened

IF [IGN] = "OFF" THEN [Speed] = 0;
IF [Gear] = "P" THEN [Speed] = 0;
```

- 값은 동치 클래스 대표값과 경계값에서 고른다.
- 물리적으로 불가능한 조합은 제약 조건으로 제외한다(실행 불가능한 케이스를 만들지 않기 위해).
- 차수: 기본 `/o:2`. 안전 관련 상호작용이 의심되면 해당 파라미터만 `/o:3` 또는 하위 모델로 강화할 수 있다.
- 시드(`/r:<seed>`)를 고정해 결과를 재현 가능하게 한다.
- 각 결과 행의 예상 출력은 요구사항에 따라 개별적으로 써야 한다. 행마다 같은 "정상 동작"을 붙이지 않는다.

## WoW 검증 (엣지 케이스)

명세의 정상 흐름 밖에서 실제 결함이 자주 나는 지점을 노린다. 베이시스 항목마다 아래 질문을 해 보고 의미 있는 것만 케이스로 만든다.

- **시간**: 초기화 직후 첫 주기, 타이머·카운터 롤오버, 주기 경계에서 입력 변화, 장시간 연속 동작
- **전원**: 동작 중 저전압·리셋·IGN 순간 차단, 복귀 후 상태 복원
- **통신**: 메시지 누락·지연·중복·순서 바뀜, 타임아웃 경계, 버스 오프 후 복귀
- **상태**: 상태 전이 도중 다른 이벤트, 같은 이벤트 연속 발생, 허용되지 않은 전이 요청
- **동시성**: 여러 요구사항이 같은 출력을 동시에 제어하려 할 때의 우선순위
- **값**: 신호 최대/최소 표현값, invalid/SNA 값, 값의 급격한 변화

WoW 검증 케이스는 보통 베이시스에 명시되지 않으므로 `suggested: true`로 둔다. 요구사항이 해당 상황의 기대 동작을 정의하지 않으면 예상 출력을 지어내지 말고 검토 의견에 "기대 동작 정의 필요"로 남긴다(그 케이스는 기대 동작이 정해질 때까지 만들지 않는다).
