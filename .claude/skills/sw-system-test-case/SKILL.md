# SW 시스템 테스트 케이스 생성

요구사항(테스트 베이시스)에서 **바로 실행할 수 있는** SW 시스템 테스트 케이스를 만든다.
결과물은 심사(A-SPICE assessment, ISO 26262 confirmation review)에서 제시할 수 있는 수준이어야 한다.
즉, 모든 케이스가 근거 요구사항으로 추적되고, 어떤 기법으로 도출했는지 설명되고, 합격/불합격을 객관적으로 판정할 수 있어야 한다.

표준 요건의 상세 내용은 `references/standards.md`, 기법별 도출 규칙은 `references/techniques.md`에 있다.
처음 사용할 때 두 파일을 모두 읽는다.

## 작업 흐름

### 1. 입력 파악

- **테스트 베이시스**: 사용자가 준 요구사항 문서(SRS, SW 요구사항 사양서, 인터페이스 사양 등)에서 시험 대상 항목을 모두 뽑아 ID 목록을 만든다.
  문서에 ID가 없으면 임의로 만들지 말고 사용자에게 ID 체계를 묻거나, `TB-001` 형식으로 붙이고 원문 위치(절/문장)를 함께 기록한다.
- 각 항목을 **기능 / 비기능**으로 분류한다. 비기능은 타이밍·응답 시간, 주기, 자원(CPU·메모리 사용률), 신뢰성·고장 대응(fault injection), 진단, 시동/종료, 통신 부하 등이다.
- **ASIL**이 주어졌으면 기록한다. ASIL이 높을수록 ISO 26262가 요구하는 방법(고장 주입 시험 등)이 강해진다.
- **양식**: 사용자가 테스트 케이스 양식(xlsx, csv, 표 등)을 줬으면 그 열 구성과 용어를 그대로 따른다. 없으면 아래 "기본 양식"을 쓴다.
- **시험 환경**: HIL, SIL, 실차, 벤치 등 주어진 환경을 확인한다. 절차와 입력은 그 환경에서 실제로 조작·관찰할 수 있는 신호로 써야 한다.

입력이 모호하면(값 범위·단위·허용오차·타이밍이 없는 요구사항 등) 추측해서 채우지 말고 `findings`(검토 의견)에 기록한다.
요구사항의 결함을 찾아내는 것도 시험 설계의 중요한 산출물이다.

### 2. 테스트 케이스 도출

각 베이시스 항목마다 아래 순서로 생각한다.

1. **동치 분할(필수)**: 입력·상태마다 유효/무효 동치 클래스를 정의하고 클래스당 대표값 하나로 케이스를 만든다. 무효 클래스는 한 케이스에 하나씩만 넣는다(여러 무효 값이 섞이면 어느 값 때문에 실패했는지 알 수 없다).
2. **경계값 분석(필수)**: 순서가 있는 입력(수치, 시간, 카운트, 길이)의 모든 경계에서 경계값과 그 바로 바깥 값을 시험한다. 해상도(LSB, 타이머 tick)를 고려해 "바로 바깥"을 구체적인 값으로 쓴다.
3. **페어와이즈(적용 가능할 때)**: 서로 독립적인 이산 파라미터가 3개 이상이라 전수 조합이 비현실적이면 적용한다. **반드시 PICT로 생성**하고 손으로 조합을 만들지 않는다. 방법은 아래 "PICT 사용"을 따른다. 적용하지 않았다면 그 이유를 요약에 쓴다.
4. **엣지 케이스 → 기법명 `WoW 검증`**: 명세에 직접 드러나지 않지만 실제로 결함이 잘 나는 상황이다. 예: 전원 리셋·저전압 중 동작, 상태 전이 도중 입력 변경, 동시 이벤트, 타이머 오버플로·롤오버, 통신 신호 누락·지연·순서 뒤바뀜, 초기화 직후 첫 주기, 최댓값 연속 입력, 진단 고장 동시 발생. 이 케이스들의 사용 기법에는 `WoW 검증`이라고 적는다.
5. **비기능 요구사항**: 측정 방법, 측정 횟수, 부하 조건, 허용 기준을 구체적으로 정한다. 안전 관련 항목은 고장 주입 시험을 고려한다(`references/standards.md` 참고).

#### 제안 케이스

베이시스에서 직접 도출되지 않고 **내가 추가로 판단해 넣는 케이스**(대부분의 WoW 검증 케이스, 추가 강건성 시험 등)는 `suggested: true`로 표시해 "제안"으로 구분한다.
제안 케이스도 가장 관련 있는 베이시스 ID에 추적시킨다. 연결할 베이시스가 없다면 그건 요구사항 누락이므로 `findings`에 "요구사항 추가 필요"로 기록한다.

#### 품질 기준: 실행 가능하고, 쓸모 있는 케이스만

커버리지 숫자만 채우는 케이스는 시험 시간을 낭비하고 진짜 결함을 가린다. 각 케이스를 쓰기 전에 다음을 확인한다.

- **고유한 목적이 있는가?** 이미 있는 케이스와 같은 클래스·같은 경계·같은 동작을 확인한다면 만들지 않는다. 같은 동치 클래스의 대표값을 여러 개 넣지 않는다.
- **입력이 구체적인가?** "적절한 값", "정상 범위의 값"이 아니라 `차속 = 120 km/h`, `CAN 0x1A0 byte2 = 0xFF` 같은 실제 값과 단위.
- **절차가 재현 가능한가?** 시험자가 혼자 따라 할 수 있도록 사전조건 → 조작 → 대기 시간 → 관찰 순서로 번호를 매긴다.
- **예상 출력이 판정 가능한가?** "정상 동작한다", "올바르게 처리한다"는 금지. 관찰 신호, 기대값, 허용오차, 시간 제한(예: `200 ms 이내 Warning_Lamp = ON`)을 쓴다.
- **환경에서 실행할 수 있는가?** 시험 환경에서 주입·관찰할 수 없는 내부 변수에 의존하면 관찰 가능한 대체 신호를 쓰거나, 불가능하면 `findings`에 기록한다.

### 3. 데이터 작성 → Excel 생성 → 검증

도출한 결과를 `references/data-format.md`의 JSON 형식으로 작성한 뒤 스크립트로 Excel을 만든다.

```bash
python <skill-dir>/scripts/build_workbook.py <data.json> -o <출력.xlsx>
# 사용자 양식이 있을 때:
python <skill-dir>/scripts/build_workbook.py <data.json> -o <출력.xlsx> --template <양식.xlsx> --header-row 1
```

스크립트는 Excel을 만들기 전에 다음을 검증하고, 실패하면 오류를 출력하고 파일을 만들지 않는다.

- 모든 테스트 케이스가 존재하는 베이시스 ID에 추적되는지 (추적성 100%)
- 시험 가능한 모든 베이시스 항목이 제안이 아닌 케이스로 1개 이상 커버되는지 (커버리지 100%)
- 필수 항목이 비어 있지 않은지, 예상 출력에 "정상", "올바르게" 같은 판정 불가 표현만 있지 않은지
- 케이스 ID 중복, 입력·예상 출력이 똑같은 중복 케이스가 없는지
- 경계값 분석, 동치 분할, WoW 검증이 쓰였는지

오류가 나면 검증 규칙을 우회하지 말고 케이스를 고친다. 시험 불가능한 요구사항 때문에 100%를 채울 수 없다면 `testable: false`와 사유를 적고, 커버리지를 정직하게 보고한다. 억지 케이스로 채우지 않는다.

생성되는 시트:

| 시트 | 내용 |
|---|---|
| 기능 테스트 | 기능 테스트 케이스 |
| 비기능 테스트 | 비기능 테스트 케이스 |
| 추적성 매트릭스 | 베이시스 ↔ 테스트 케이스 양방향 추적 |
| 커버리지 요약 | 베이시스 커버리지, 기법별 케이스 수 |
| PICT 모델 | 사용한 PICT 모델, 옵션, 시드 (페어와이즈를 썼을 때) |
| 검토 의견 | 요구사항 모호·누락·시험 불가 항목 |

제안 케이스는 `구분` 열에 "제안"으로 표시되고 행이 노란색으로 강조된다.

## 기본 양식

사용자 양식이 없을 때의 열: **테스트 케이스 ID, 테스트 베이시스 ID, 구분(기본/제안), 테스트 목적, 사전조건, 입력값, 절차, 예상 출력값, 합격/불합격 기준, 사용한 테스트 기법**, 그리고 값이 있을 때 시험 환경, ASIL, 우선순위, 비고.
사용자가 요청한 7개 항목(ID, 베이시스 ID, 목적, 입력값, 절차, 예상 출력값, 기법)은 항상 포함한다. 사전조건과 합격 기준은 A-SPICE가 요구하는 내용이라 기본으로 넣는다.

ID 규칙(사용자 규칙이 없을 때): 기능 `STC-F-001`, 비기능 `STC-NF-001`.

## PICT 사용

페어와이즈 조합은 Microsoft PICT(https://github.com/microsoft/pict)로만 만든다. 손으로 만든 조합은 쌍 커버리지가 보장되지 않기 때문이다.

1. PICT 모델 파일을 작성한다. 출력 인코딩 문제를 피하려고 파라미터 이름과 값은 영문·숫자로 쓴다(한글 설명은 테스트 케이스에 쓴다). 파라미터 값은 동치 클래스의 대표값과 경계값을 사용하고, 불가능한 조합은 제약 조건(`IF ... THEN ...;`)으로 제외한다. 문법은 `references/techniques.md` 참고.
2. 실행한다:
   ```bash
   python <skill-dir>/scripts/run_pict.py <model.txt> --out <result.tsv> --seed 1
   ```
   PICT가 없으면 스크립트가 안내 메시지를 출력한다. 사용자에게 알리고 동의를 받은 뒤 `--download`를 붙여 GitHub 공식 릴리스의 `pict.exe`를 받는다(Windows). 다른 OS는 소스에서 빌드해야 한다.
3. 결과의 각 행을 테스트 케이스 하나로 옮기고, 기법에 `페어와이즈(PICT)`를 적는다. 모델·옵션·시드는 JSON의 `pict_models`에 넣어 재현할 수 있게 한다.
4. PICT 결과 행을 임의로 빼거나 바꾸지 않는다. 조합을 바꿔야 하면 모델(제약 조건)을 고쳐서 다시 생성한다.

## 최종 보고
